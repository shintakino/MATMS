# Other-module usability review

Reviewed 2026-11-03 after the shared visual refresh and Property Inventory guidance. This records the source-based findings before implementation; the follow-up below tracks implementation. It is not a school-user study. Earlier accessibility scans do not measure task comprehension.

| Priority | Module | Observed behavior and impact | Proposed improvement and acceptance |
| --- | --- | --- | --- |
| High | Printed template stock | `inventory-register.tsx` labels the submit button **Review stock operation**, but receive, issue and transfer call the mutation immediately; only balance correction opens a review dialog. The action wording suggests a review step that does not exist for most operations. Transfer destination and superseded-stock decision fields remain visible for every action. | Either provide an explicit review/confirm step for each action or label direct actions accurately. Show only applicable fields. Verify that opening a review never posts stock and that changing action clears stale review state. |
| High | Template-stock setup | `archive-intake.tsx` explains that a designated template folder is required, but its Folder selector maps the complete returned folder list without checking the template designation. The server rejects ineligible folders. | Offer eligible choices, explain why stock setup needs a designated folder, and link to the setup steps when none exist. Verify the empty/error states and preserve server authorization. |
| High | Requests and loans | `custody-workspace.tsx` presents permitted documents as one scrollable checkbox list without search or a selected-document summary. Request details expose line actions but have no overall next-step guidance. Loan forms mix returns and exception handling on the same cards. | Add an authorized searchable document picker and visible selection summary; guide Draft → Submit → Decide → Fulfill/Release → Return. Keep partial line outcomes and physical return versus exception resolution distinct. Verify mixed requests, restricted approval and selection retention. |
| High | User administration | `admin-user-management.tsx` collects assisted-reset passwords through `window.prompt`, which provides an ordinary visible text entry without the application's validation, confirmation and contextual explanation. | Use a masked-password dialog with validation, the selected account identity, session-revocation consequences and persistent errors. Explain account roles beside account creation. Verify cancel, failure, focus return and assisted-reset enforcement. |
| Medium | Archive filing | `archive-intake.tsx` shows all optional document metadata immediately and uses a long native folder selector. No guided location → box → folder → document setup or success link is provided by the intake forms. | Add prerequisite guidance and searchable folder selection with full location context. Collapse optional metadata without losing values; provide a link to the saved record. Verify both internal and restricted filing. |
| Medium | Restricted access | `access-workspace.tsx` uses native account/record lists and explains inherited restrictions in prose; it does not show a selected record's full access path or which other restricted levels still need grants. | Preview the selected account, target and authorized ancestry, distinguishing this grant from effective access. Link to remaining required grants where authorized. Verify independently restricted ancestors and descendants; preserve server enforcement. |
| Medium | Search and reports | `reporting-workspace.tsx` presents a large filter grid together. Its date labels do not explain which date the chosen report uses; empty results give generic filter guidance. | Keep common filters visible, disclose advanced ones, summarize active filters and explain report-specific dates and export scope. Verify URL restoration and exported rows against the visible authorized filter scope. |
| Medium | Audit and settings | `audit-workspace.tsx` expects exact action/type strings and actor IDs. `settings-workspace.tsx` uses **Canonical HTTPS origin** and displays school identity, session policy and QR migration controls in one form. | Provide actor/action pickers and readable event descriptions while retaining technical details on demand. Group settings by purpose and explain **Public website address used by QR labels** alongside the technical term. Verify that labels and values preserve the existing policies. |

Recommended implementation order: correct template-stock action expectations and setup choices; guide requests/loans; replace password-reset prompts; then improve archive intake, access previews and report/admin filters. Reuse the shared guidance and disclosure patterns, keeping business authorization, transactions, durable operation IDs and audit behavior in the existing services.

## Implementation follow-up — 2026-11-04

All eight finding areas now have application changes: explicit stock confirmation and relevant fields; eligible template folders and prerequisite links; paged request selection, selected summaries and custody guidance; a masked reset dialog; searchable archive destinations, optional metadata and saved-record links; protected ancestry previews with links to missing parent grants; advanced report filters with scope/date help; and actor/action audit choices, readable events and grouped settings. Verification passed: 49 reporting/access integration assertions, strict web types, server/web production builds, four individual browser scenarios covering stock/custody, filing, account reset and administration, 13 core-route accessibility scans plus the reset dialog, and five mobile layout checks. See the progress tracker for evidence. Actual school-user testing remains a pilot activity.
