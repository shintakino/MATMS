## Selected stack

The scheduling revision replaces account-bound beneficiaries with a separate SHS/JHS/personnel directory, snapshots beneficiaries independently of filing accounts, and restricts internal resource operations to Admin. Linked non-Viewer personnel can file leave on behalf of any directory person and manage their filed/self requests. Admin-only public invitations use hashed 256-bit fragment tokens, expiry/revocation, teacher identity/version binding and one atomic use. Public requests have no authenticated actor; their audit records retain the invitation/issuer provenance without impersonating the Admin. Submission, consumption, holds and audit use the existing scheduling transaction lock; exact retries retain an opaque receipt. Persistent global/per-IP throttles protect the bounded POST-only public capability endpoints. See spec 14 for the active contract and progress tracker for implementation state.

Existing combined-teacher capacity remains an additional configurable ceiling alongside new SHS/JHS limits. Legacy unclassified teacher holds count conservatively against both divisions until resolved; historical snapshots and creation fingerprints remain unchanged. The migration replaces account-based leave overlap exclusion with beneficiary-person exclusion. Future active request edits retain separate durable edit receipts, revalidate their full date range, reset approval and remove approved public listings until reapproval; the original creation fingerprint stays immutable. Existing archive, inventory and physical custody domains remain separate. Public ordinary calendars keep their opt-in allowlists; invitation-scoped availability does not grant directory, private-register or account access.

Scheduling's reviewed migration installs PostgreSQL `btree_gist` and adds partial exclusion constraints for inclusive resource and same-person leave date overlaps. All category-capacity mutations use the scheduling lock. Linking/reactivating equipment share-locks its inventory item/lot; inventory retirement's existing update lock checks active bookable links before deactivation. Resolve reservations and retire a bookable unit before deactivating its source. This adds no ledger or physical-custody writes. Public RPC output schemas validate allowlists and scheduling HTTP responses use `private, no-store`.

## Boundaries and request flow

Browser → HTTPS reverse proxy → Next.js web or Hono server → PostgreSQL.

Use one public origin: `/api/auth/*` routes to Better Auth on Hono; `/rpc/*` routes to oRPC through Next rewrites. Next.js owns presentation; Hono/domain procedures own authorization, business rules, transactions, and database access. Server-rendered data requests use the same authorized service boundary. ## Storage and domain model

- PostgreSQL holds application records and history; Better Auth owns credential/session tables. Application user foreign keys must match generated auth ID types, even though application records use UUIDs.
- Shelf location → box → folder → document is the physical home hierarchy. Box category classifies descendants. A checked-out item retains its home ancestry while its custody is tracked separately.
- A template row is one revision. Inventory is unique per revision/folder pair and is allowed only in template folders. Digital revision changes do not relabel existing printed stock.
- `stock_operations` deduplicates mutation intent; `stock_transactions` is the append-only ledger. Request lines, checkouts, movement events, and audit logs preserve operational history.
- Stock keeps the PRD's `stock_operations` model. Release and return use a separate durable `custody_operation_replays` table with a unique UUID operation ID, operation kind (`release` or `return`), actor ID, authorized scope fingerprint, payload fingerprint, saved result JSON, and timestamp. A replay is reauthorized before returning its saved result; an ID reused with a different payload fails.
- Store digital master/document links as validated HTTPS URLs. Do not fetch arbitrary URLs server-side. There is no general archive blob/file store. PRD v1.3 adds a narrow private staging/artifact lifecycle for controlled inventory imports and official exports; provenance and immutable report data remain durable after temporary bytes expire.
- Container ancestry determines effective location. Movement events preserve source/destination references or label snapshots instead of rewriting descendant histories.

The complete table and constraint baseline is PRD §8; feature specs refine it without replacing its controls.

## Authorization

- The `property_custodian` account role is present in the schema and account controls. Existing archive operations treat it as a non-Admin role subject to inherited grants; authorized custodial services permit it alongside Admin. Comprehensive role-path verification remains in progress.
- The initial form-profile table stores append-only, versioned definitions; a PostgreSQL trigger rejects update and delete. Creation is an authenticated Admin-only, audited, replay-safe service. Profiles can include reference-based geometry, heading styles and optional default signatories. A school approval reference is recorded with each version; source-render fidelity and complete layout requirements remain open.
- Initial physical-count session, line, assignment and omission tables constrain profile-family matching, line membership, assignment scope and line status. Database triggers prevent changes to finalized sessions and their children. Services create and refresh draft snapshots, record reason-bearing membership omissions, manage Staff assignments, save observations, finalize a reviewed payload and create linked amendments; authenticated RPC procedures expose these operations with the same server-side authorization. The paged count list returns assigned drafts only for Staff. Finalized payloads retain membership omissions and amendments copy them into the new draft. Source mutations take a shared transaction advisory lock; finalization takes the exclusive counterpart before revalidation. All future source mutations must follow the same lock order. The current readiness policy is conservative and profile/layout, concurrency and UI remain incomplete; these procedures do not establish count acceptance.
- Assigned count entry includes a separate reviewer note. It is frozen with the count and copied into amendments, but it does not grant review approval or satisfy the manager's resolution requirement.
- Classification thresholds now have immutable, effective-dated Admin-authored policy versions. Staged RPCSP imports must reference a policy; their evidence retains the selected policy and threshold, and count commits reject a policy that was not yet effective on the count date. Workbook uploads use an authenticated, origin-checked binary endpoint with size, concurrency and time limits before isolated parsing. Authenticated import screens expose staging, resolution and explicit commit; complete adversarial and workflow verification remains in progress.
- Report sections are Admin-managed with effective dates, optimistic versions and audited changes. Draft count fingerprints include section identity, version and display configuration; a changed section requires an explicit refresh and line review before finalization.
- Generated inventory workbooks retain an immutable canonical payload, data hash, original checksum and private database artifact with seven-day expiry. Finalized payloads pin renderer version v1 and effective default options; future renderer versions must retain the v1 path for historical regeneration. Generation, previews and authorized downloads are audited; after the retained bytes expire, downloads regenerate from the same snapshot and record the new checksum. Source-render fidelity, pagination and full official-form acceptance remain unverified.
- Authenticated custodial inventory RPC procedures expose bounded item lookup, item details, version-checked item/lot maintenance, lot/balance creation, property-number exceptions, dated stock-card reads and stock postings. Prior item codes remain reserved; units cannot change once a lot or balance exists, and stock-bearing items/lots cannot be made inactive. Item results keep office balances separate and apply register filters to both membership and returned scopes. Active Staff and Viewers may read current items; Viewers cannot read stock-card history, while writes remain restricted to Admin and Property Custodian. Back-dated postings require a confirmed impact preview whose hash binds the intent, balance versions and chronological ledger; the transaction rejects stale previews. Full inventory acceptance and broader UI verification remain incomplete.
- ExcelJS renders count and Stock Card workbooks from authorized server snapshots, and authenticated endpoints provide audited previews, private downloads, print views and artifact history. Reference-based count profiles have checked header merges, border edges and typography; complete source-rendered fidelity and pagination acceptance remain open. Controlled import uses SheetJS in a separate Linux process with a 512 MiB address-space limit, timeout, capped input/output and concurrency, and streamed ZIP preflight. Authenticated upload, resolution and atomic draft-count, verified-opening, combined and historical-ledger commit operations are routed. Staged raw bytes have a provisional seven-day expiry; periodic cleanup retains committed provenance and removes expired staged details. Policy, distributed limits and full adversarial verification require further review.
- Admin provisions accounts; no public signup. Bootstrap the first Admin without committed credentials. Prevent removing the last active Admin.
- Validate active account/session, role capability, and object scope at every procedure. Deactivation revokes sessions and retains historical attribution.
- Classifications are `internal` and `restricted`. Admin has schoolwide access. Other users need grants satisfying every restricted ancestor and any independently restricted target. A parent grant covers descendants unless a descendant is independently restricted; a child grant cannot bypass a restricted parent.
- Filter before pagination, aggregation, search suggestions, reports, exports, print selection, and recent activity. Inaccessible IDs produce generic unavailable responses.
- Staff cannot grant access or downgrade confidentiality. A move into less restrictive ancestry needs Admin review. History payloads and request lines must not leak inaccessible related records.
- UI visibility is convenience only; all permissions are enforced on the server. Successful sign-in/sign-out cancels and clears browser queries so cached private results cannot cross accounts; sign-out retains only a local module continuation.
- Dashboard, search, reports, and CSV share a server-side scoped query layer. Record ancestry and related request visibility are resolved before aggregation and pagination; operational history and exports are unavailable to Viewers. Successful ordinary CSV exports are audited before release, capped at 5,000 filtered rows, and subject to a persistent per-account attempt limit. The cap is provisional pending pilot review. Official custodial XLSX/print exports follow their own authorized immutable snapshot and generation limits in spec 12; CSV permission never grants official-form generation.
- QR labels contain only the configured HTTPS canonical origin and stable box UUID; label metadata is limited to authorized box-level fields and is denied to Viewers. The singleton school settings override the initial deployment-origin fallback; changing the saved origin requires an audited redirect/reprint plan. Camera results must match that exact origin and a box UUID route. Manual code lookup and the resulting box page independently enforce current access. Preserve old-origin redirects to the same UUID paths until printed labels are reissued.

## Transaction and lifecycle invariants

1. Stock balances, ledger, and audit commit together. Use conditional updates or row locks, never an unguarded read-modify-write. Counts and thresholds are nonnegative integers.
2. Transfers atomically debit and credit the same revision with linked ledger entries. Corrections require Admin, reason, and expected version.
3. Stock, release, return, and transfer operations have an operation ID and payload fingerprint. Identical retries return the original authorized result; different payloads with the same ID fail. Recheck access before returning a replayed result.
4. One document can have at most one unresolved open loan, enforced in PostgreSQL. Repeated release/return cannot duplicate custody changes. Request progress and related audit update atomically with fulfillment.
5. Audit failure rolls back its business mutation. Audit and ledger entries are append-only through the app; do not cascade-delete operational/history records.
6. Stable UUID QR targets survive editable code changes. Normalize unique codes and never reuse retired codes.
7. Archived boxes accept returns of existing loans but no new filing or routine inventory operations until reactivated. Retirement requires resolved active requests/loans and zero inventory or prior relocation/resolution.
8. Documents cannot be refiled while checked out. Alternative return locations create a movement event in the return transaction.
9. Event timestamps are UTC, displayed in Asia/Manila. Date-only metadata must not shift by timezone. Overdue is derived from an open loan and its due timestamp.
10. Category and shelf-location edits update their shared reference records transactionally with audit. Current records resolve the edited values by reference; prior movement snapshots remain historical facts.
11. Lifecycle changes, filing, folder moves, and inventory updates coordinate on the affected box lock; stock mutations recheck their authorized active scope inside their transaction. Retirement and refiling reject physically unreturned loans even when an exception has been administratively resolved, and reject returned loans with unresolved exceptions. Folder/document retirement also rejects active requests; folder retirement rejects nonzero inventory and active documents. Audit writes commit with the lifecycle/settings change.
12. The singleton school settings hold audited Admin-configurable session idle and maximum limits, defaulting to 30 minutes and 12 hours. Backend auth instances track the saved idle policy; protected context checks policy before refreshing and enforces the maximum lifetime. Server-rendered checks do not consume cookie refreshes; browser responses forward renewed cookies.

Search walks indexed code order for scoped box/folder/document candidates, checks authorization and filters before pagination, and limits each inventory revision's authorized candidates before merging. All-type search merges bounded domain results in deterministic C-collation code/kind/ID order. Query performance must still be measured against the representative dataset; an index's existence is not acceptance evidence. The shell owns the page's main landmark; feature components use sections inside it.

Application PostgreSQL pools disable JIT compilation per connection. Representative operational search plans spent substantially more time compiling than executing; this setting targets short interactive queries and does not change authorization or transaction semantics.

Type-check caching is limited to declaration files/maps and TypeScript build metadata. It must not restore runtime `dist` bundles; builds own executable outputs.

Production web builds use Next.js's webpack builder after the installed Turbopack optimized build failed to make progress in this environment. Development still uses Turbopack. Strict workspace type checks remain separate from Next's compatibility-configured build; a successful build does not substitute for those checks.

## Operations

Automatic deployment was authorized and verified on 2026-11-04. The workflow runs isolated checks/browser tests and builds immutable GHCR image digests on GitHub-hosted runners, then updates the existing MATMS Coolify Service. Production environment values and volumes remain in Coolify. A separate Cloudflare deployment gateway exposes only the fixed MATMS service status/update/restart/storage routes and this host's registry-login route; the dashboard and unrelated resource routes are outside its tested ingress allowlist. A scoped `read`/`write`/`deploy` Coolify token is stored as a main-only production-environment Actions secret. Image pulls use the deploy job's short-lived package token and cache immutable digests locally. Coolify's API remains enabled for this automation. Deployments are serialized; an encrypted backup must succeed before migrations. The public web build ID and Hono readiness revision/deployment-attempt ID prevent old containers from satisfying a new rollout, including reruns of the same Git SHA. Successful run `41775997721` verified the complete path and preserved the permanent Admin and volume identities. Routine Compose replacement still briefly interrupts service; zero-downtime operation is not claimed.

The initial 2026-11-04 deployment uses a dedicated Coolify Service on the existing Ubuntu host: Cloudflare HTTPS → a dedicated outbound tunnel → private Next.js web → Bun/Hono → PostgreSQL. The production template is `deploy/docker-compose.coolify.yml`. It publishes no application or database host ports. A one-shot migration service uses the database owner; the runtime uses a separate non-owner `matms_app` role, and the web/API processes run as unprivileged users. Coolify stores production environment values; source workbooks and private operator files are excluded from images. Local release images are built from the reviewed workspace rather than publishing uncommitted source. A dedicated backup container writes encrypted daily dumps to a separate Docker volume with 30-day retention. Off-host backup delivery is not configured and remains an operations requirement. Startup, public login and restore verification are recorded separately in the progress tracker.

The production web build binds an HTTP-to-HTTPS redirect to the configured canonical hostname and trusted forwarded protocol. Private health requests continue over internal HTTP without depending on the tunnel. The redirect origin, like the Next rewrite destination, requires a rebuild when its configuration changes.

Keep PostgreSQL private to the container network. Deploy reviewed migrations as one controlled release task, not per replica or through production schema push. Pin images/toolchains and use separate web/server builds; verify Next.js runtime support rather than assuming Bun everywhere.

Provide liveness/readiness, structured redacted logs, connection pooling, timeouts, graceful shutdown, backup monitoring, and rollback instructions. Daily encrypted off-host backups with 30-day retention, RPO ≤24 hours and staffed-support RTO ≤4 hours are proposed targets pending school confirmation. Rehearse restoration before launch and quarterly. Persistent volumes are not backups.

## Planned Property Custodian extension — PRD v1.3

[Specs 10–13](feature-specs/README.md) extend the existing workspace. Keep Next.js as presentation and Hono/oRPC as the authorized business, parsing and generation boundary. Add domain contracts/services in `packages/api`, reviewed Drizzle storage in `packages/db` and feature/print composition in `apps/web`. ExcelJS is pinned for the draft XLSX writer; SheetJS is pinned for trusted source inspection. Bounded isolation for untrusted BIFF/OOXML import and any job system remain to be designed and verified.

- Separate `custodial_items`, lots, balance ownership, operations and transactions from `templates`, `template_inventory` and `stock_transactions`. Item/fund/office balances and lot/property identity never depend on archive folder ancestry. A lot has one reporting class; effective-dated sections and threshold policy govern future classification only.
- Persist nonnegative versioned balances with uniqueness for item/lot/fund/office scope, including null-lot cases. Transactions and durable replay record effective date, posted time/sequence, reference, actor, fingerprints and before/after posting facts. Transfers lock/debit/credit/audit atomically and never change class or unit. Nullable values/reorder points remain distinct from zero; use fixed-decimal currency and text identifiers.
- Append-only posting facts and chronological cards are separate views of the same deltas. Back-dated writes lock/reconcile the effective-dated stream, reject any intermediate negative projected balance and recalculate later card balances without rewriting posted ledger facts. Preserve frozen historical exports.
- Physical-count sessions/lines freeze authorized as-of quantities, identifiers, valuation, conditions, acquisition fields, metadata, signatories and profile version. Draft refresh is explicit and audited; stale source changes require review. Persist Staff assignments and line versions. Finalization locks an immutable snapshot; amendments link a new session and reason. Count variances never automatically post stock adjustments.
- Profiles are versioned immutable layout/configuration records after use. Exports retain canonical report payload/reference, profile version, data hash and generated-byte checksum. Stock cards freeze their ledger/metadata projection separately from count sessions. Regeneration uses frozen data; temporary-byte expiry cannot destroy reproducibility or export history.
- Inventory import batches/rows retain source hash, coordinates, raw/mapped evidence, resolutions and commit identity. Preview changes staged evidence only. Commit revalidates target versions and role/scope and atomically writes selected openings/draft counts plus audit; identical retries cannot duplicate balances. Importing historical ledger and its ending balance must not double-post opening stock.
- Private inventory file staging and authorized downloads are the only new file-handling scope. Bound parsing/resource use, reject unsupported/encrypted/macro-enabled inputs, never execute uploaded formulas or external links, and expire temporary bytes under documented policy. Ordinary archive files remain external HTTPS links.
- Add `property_custodian` to the application profile role and enforce PRD §5 across existing record/template/custody workflows as well as new services. Role does not imply archive grants or Admin authority. Staff custodial work is explicit assigned draft entry only; posting/finalization/import/official export belongs to Admin/Property Custodian. Verify permission revocation on downloads and saved operation replays.

Read [inventory-workbook-reference.md](inventory-workbook-reference.md) for exact source sheets, column/header geometry, signatories and anomalies. The source-faithful RPCSP profile retains `SHORTAGE/COVERAGE`; calculation always uses physical minus card and signed fixed-decimal value. Source formulas/variances/totals are untrusted. School profile/threshold approval is a production policy gate; fictional development can proceed.

Target sizing adds 10,000 custodial items/lots, 250,000 ledger rows and 100 count sessions. Measure new query paths separately from the existing archive benchmark. A 2,000-line XLSX/preview must complete within 30 seconds on the agreed profile or use a visible, authorized, idempotent queued job. Backups/restore include new snapshots, profiles, provenance and retained artifacts when applicable.

## Administrative usability queries

The authorized folder-choice response includes the template-folder designation and shelf label so the UI can restrict stock setup choices and show complete filing context. A protected Admin-only access-preview query reads the selected account, record ancestry and active grants to explain present access and the effect of granting only the target. It does not grant access or replace authorization at mutation/read time. Independently restricted descendants are explicitly outside this ancestry preview. An Admin-only audit-choice query returns distinct action and target-type codes for filters; audit actor choices reuse authorized account administration. No new storage domain or schema is introduced.
